# Система бронирования переговорных комнат

REST-сервис на **Java 21 / Spring Boot 3.5.0**, Spring JDBC и **H2 in-memory**. Сборка — **Gradle 8.14.3 с Kotlin DSL**; код приложения — Java.

## Запуск в Docker

Требуются Docker и Docker Compose. Установленные на компьютере Java и Gradle не нужны.

```sh
docker compose up --build -d
```

API доступно по адресу `http://localhost:8080`. Проверка:

```sh
curl -i http://localhost:8080/api/bookings
```

При первом запуске возвращается `200 OK` и `[]`. Образ собирается в два этапа: Gradle компилирует проект и выполняет тесты, затем JAR копируется в образ Java 21 JRE. Приложение работает от непривилегированного пользователя.

```sh
docker compose logs -f
docker compose down
```

Альтернатива без Compose:

```sh
docker build -t meeting-rooms .
docker run --rm -p 8080:8080 meeting-rooms
```

## Кеширование сборки

Локально `docker compose build` и `docker compose up --build -d` используют кеш слоев BuildKit автоматически. В Dockerfile сначала копируются файлы конфигурации Gradle и Wrapper, затем задача `resolveDependencies` скачивает дистрибутив Gradle, плагины и JAR-зависимости. Исходники копируются после этого шага. Изменение Java-кода пересобирает приложение, но сохраняет слой с зависимостями. Изменение файлов сборки или Wrapper обновляет этот слой. Полностью неизмененная сборка переиспользует готовые слои, включая результат запуска тестов.

Зависимости сохранены именно в слое сборки: он переносится в кеш GitHub вместе с остальными промежуточными слоями. Обычные `RUN --mount=type=cache` сами по себе не сохраняются между GitHub runners, поэтому здесь они не используются. Подробнее: [кеширование Docker в GitHub Actions](https://docs.docker.com/build/ci/github-actions/cache/).

Проверить попадания в локальный кеш можно двумя последовательными запусками:

```sh
docker compose --progress plain build
docker compose --progress plain build
```

Во втором логе шаги сборки будут отмечены `CACHED`. Кеш привязан к выбранному Docker builder и сохраняется до его очистки или автоматического удаления старых данных. Для полной пересборки без кеша Docker: `docker compose build --no-cache`.

В `gradle.properties` включен Gradle Build Cache: обычные локальные сборки переиспользуют результаты задач из `~/.gradle/caches`, даже после `clean`. Зависимости и Wrapper также хранятся в `~/.gradle`. В GitHub эти данные сохраняет `setup-gradle`; запись разрешена при push в любую ветку, для pull request кеш Gradle используется только для чтения.

## Локальная сборка

Требуется JDK 21. Gradle Wrapper включен в проект и скачивает закрепленную версию Gradle автоматически; отдельно устанавливать Gradle не нужно. Для первой сборки нужен доступ к интернету.

```sh
./gradlew clean build
java -jar build/libs/meeting-rooms.jar
```

Для разработки: `./gradlew bootRun`. Для запуска тестов: `./gradlew test`. В Windows используйте `gradlew.bat` вместо `./gradlew`.

HTML-отчет тестов: `build/reports/tests/test/index.html`.

## CI

Workflow `.github/workflows/ci.yml` запускается в GitHub Actions при каждом push в любую ветку, а также для pull request. На Ubuntu с Java 21 выполняется `./gradlew --no-daemon build`: компиляция, все интеграционные тесты (включая конкурентные запросы) и сборка исполняемого JAR. Внешняя база для тестов не требуется.

Gradle Actions проверяет целостность Wrapper и кеширует зависимости и результаты задач. Даже при падении тестов доступные HTML- и XML-отчеты загружаются в артефакт `test-reports` и хранятся 14 дней. Провал любого теста завершает CI с ошибкой. Для запуска достаточно отправить проект вместе с `.github` и файлами Wrapper в GitHub-репозиторий с включенным Actions; секреты не нужны.

После успешных тестов отдельная задача `docker` собирает образ через Docker Buildx. `cache-from: type=gha` восстанавливает кеш, а `cache-to: type=gha,mode=max` сохраняет все слои, включая промежуточный слой зависимостей. Используется API кеша v2 и отдельный scope `meeting-rooms`. Кеш доступен в рамках правил GitHub для текущей и основной веток; кеш pull request изолирован от обычных веток. Первый запуск или удаление кеша приводит к полной сборке. Локальный Docker и GitHub хранят независимые кеши, автоматически между собой они не синхронизируются.

Образ проверяется сборкой, но не публикуется в реестр (`push: false`); Docker Hub credentials не нужны. Если исходники не менялись, Gradle и Docker могут вернуть результаты тестов из кеша; изменения входных файлов вызывают повторное выполнение соответствующих задач.

## Бизнес-правила и обоснование

1. **Комнаты заданы заранее:** `room-1` — Альфа, `room-2` — Бета, `room-3` — Гамма. Неизвестная комната возвращает `404`. Так опечатка не создает несуществующую переговорную. Администрирование комнат вне объема задания; начальный список задается в `src/main/resources/data.sql`.
2. **Длительность от 15 минут до 4 часов включительно.** Минимум отсеивает случайные слишком короткие брони, максимум не позволяет занимать комнату на весь рабочий день. Одинаковые правила применяются к созданию и проверке доступности: проверяется именно допустимый для бронирования интервал.
3. **Начало не раньше текущего момента сервера.** Сравниваются точные моменты времени; округления до минут нет. Интервал с концом раньше начала или равным началу недопустим. Проверка времени выполняется после получения блокировки комнаты, чтобы ожидание конкурирующего запроса не позволяло создать бронь в прошлом.
4. **Время — ISO 8601 с обязательным смещением:** `2030-01-15T10:00:00Z` либо `2030-01-15T13:00:00+03:00`. Ответы нормализованы в UTC (`Z`); часовой пояс компьютера не влияет на сравнение. Это устраняет неоднозначность времени между офисами и клиентами.
5. **Интервалы полуоткрытые `[startsAt, endsAt)`.** Брони 10:00–11:00 и 11:00–12:00 совместимы: буфер на уборку не предусмотрен. Пересечение определяется условием `existing.startsAt < new.endsAt AND existing.endsAt > new.startsAt`. Оно запрещает частичное пересечение, полное вложение и совпадение.
6. **Один сотрудник может бронировать разные комнаты одновременно.** Ограничение относится к комнате, поскольку сотрудник может быть организатором нескольких встреч. `employeeEmail` обязателен и проверяется как email, максимум 254 символа. `roomId` обязателен, максимум 50 символов. Неизвестные поля JSON отклоняются, чтобы опечатки клиента не игнорировались.
7. **Отмена физически удаляет бронь и сразу освобождает интервал.** Успех — `204` без тела; неизвестный UUID и повторная отмена — `404`. Повторный DELETE не меняет состояние. Можно удалить и прошедшую бронь. Статуса `cancelled` и журнала отмен нет: аудит не входит в требования.
8. **Список содержит все неудаленные брони, в том числе прошедшие**, в порядке начала, затем UUID для однозначной сортировки. Пагинации нет согласно требованию получить все бронирования.
9. **Нет ограничений по рабочим часам, выходным и горизонту бронирования.** Они не заданы в условии; сервис не делает предположений о графике офиса.

## Защита от одновременных бронирований

Создание проходит в одной транзакции с уровнем `READ_COMMITTED`: `SELECT ... FOR UPDATE` блокирует строку комнаты, затем проверяются время и пересечения и вставляется бронь. Блокируется именно комната: это работает и при отсутствии существующих бронирований. Конкурирующий запрос на ту же комнату после ожидания видит уже сохраненную бронь и получает `409`. Разные комнаты имеют независимые блокировки.

Таймаут ожидания блокировки — 10 секунд; при его исчерпании возвращается `503` с `Retry-After: 1`. Проверка доступности — снимок текущего состояния, она не резервирует комнату. Даже после `available: true` создание может вернуть `409`, если другой клиент успел раньше.

## REST API

| Метод | Путь | Успешный ответ |
|---|---|---|
| POST | `/api/bookings` | `201 Created`, бронь и заголовок `Location` |
| GET | `/api/bookings` | `200 OK`, массив броней |
| DELETE | `/api/bookings/{id}` | `204 No Content` |
| GET | `/api/rooms/{room}/availability?startsAt=...&endsAt=...` | `200 OK`, доступность |

`id` — UUID бронирования; `room` — строковый идентификатор комнаты. `Location` идентифицирует созданную бронь и совпадает с адресом ее удаления; отдельный GET по UUID не предусмотрен.

### Создать бронирование

Даты в примерах должны оставаться будущими относительно часов сервера; при необходимости замените их.

```sh
curl -i -X POST http://localhost:8080/api/bookings \
  -H 'Content-Type: application/json' \
  -d '{
    "roomId": "room-1",
    "employeeEmail": "ivan@example.com",
    "startsAt": "2030-01-15T10:00:00Z",
    "endsAt": "2030-01-15T11:00:00Z"
  }'
```

Пример тела ответа (`id` и `createdAt` генерируются сервером):

```json
{
  "id": "b48d70d5-fc2f-4371-96fc-ec0d1426ccfb",
  "roomId": "room-1",
  "employeeEmail": "ivan@example.com",
  "startsAt": "2030-01-15T10:00:00Z",
  "endsAt": "2030-01-15T11:00:00Z",
  "createdAt": "2026-09-09T12:00:00Z"
}
```

### Получить список

```sh
curl http://localhost:8080/api/bookings
```

Ответ — массив объектов того же формата, что при создании; при отсутствии броней — `[]`.

### Проверить доступность

```sh
curl -G http://localhost:8080/api/rooms/room-1/availability \
  --data-urlencode 'startsAt=2030-01-15T13:00:00+03:00' \
  --data-urlencode 'endsAt=2030-01-15T14:00:00+03:00'
```

Используйте URL-кодирование: символ `+` в смещении должен передаваться как `%2B`.

```json
{
  "roomId": "room-1",
  "startsAt": "2030-01-15T10:00:00Z",
  "endsAt": "2030-01-15T11:00:00Z",
  "available": false
}
```

Занятая комната возвращает `200` и `available: false`, поскольку сама проверка выполнена успешно.

### Отменить бронирование

Подставьте UUID из ответа создания:

```sh
curl -i -X DELETE http://localhost:8080/api/bookings/b48d70d5-fc2f-4371-96fc-ec0d1426ccfb
```

### Ошибки

Ошибки API оформлены как `application/problem+json` (Spring `ProblemDetail`).

| Код | Причина |
|---|---|
| 400 | Некорректный JSON, email, UUID, время, длительность, неизвестные поля или отсутствующие обязательные параметры |
| 404 | Комната или удаляемая бронь не найдена |
| 409 | Пересекающаяся бронь той же комнаты |
| 503 | Истекло ожидание блокировки комнаты; можно повторить запрос |

Пример конфликта:

```json
{
  "type": "about:blank",
  "title": "Conflict",
  "status": 409,
  "detail": "Room is already booked for this interval",
  "instance": "/api/bookings"
}
```

Для ошибок валидации полей дополнительно возвращается массив `errors` с `field` и `message`.

## Проверки и устройство проекта

Интеграционные тесты запускают Spring-контекст с настоящей H2 и вызывают API через MockMvc. Часы зафиксированы, поэтому тесты не устаревают со временем. Проверяются полный цикл создания/чтения/отмены, все виды пересечений, соседние интервалы, независимость комнат, границы длительности и текущего времени, прошлое время, часовые пояса, ошибочные запросы и неизвестные ресурсы. Отдельный многопоточный тест одновременно запускает восемь реальных транзакций и проверяет, что сохранена ровно одна бронь, а остальные запросы получают конфликт.

Java-код расположен в `src/main/java/com/example/meetingrooms` и разделён по ответственности:

- `controller/` — HTTP-контракт: `BookingController` для бронирований, `AvailabilityController` для доступности комнат.
- `service/` — сценарии приложения: `BookingService` управляет бронированиями и транзакцией, `AvailabilityService` проверяет доступность.
- `repository/` — параметризованные SQL-запросы через `JdbcTemplate`: `BookingRepository` хранит и читает брони, `RoomRepository` проверяет и блокирует комнаты. Преобразование строк БД в модель остаётся в репозитории.
- `validation/` — `BookingIntervalValidator`, общие правила времени начала и длительности для обоих сценариев.
- `model/` — модель бронирования `Booking`.
- `dto/` — входной запрос `BookingRequest` и ответ о доступности `Availability`.
- `exception/` — `ApiExceptionHandler`, единый формат ошибок и обработка таймаута блокировки.
- `config/` — `TimeConfig`, настройка часов. `MeetingRoomsApplication` отвечает только за запуск.

Тесты расположены в `src/test/java/com/example/meetingrooms`:

- `integration/BookingLifecycleIntegrationTest` — создание, чтение и отмена бронирования.
- `integration/BookingOverlapIntegrationTest` — пересечения, соседние интервалы и независимость комнат.
- `integration/BookingValidationIntegrationTest` — HTTP-валидация, границы интервалов и неизвестные ресурсы.
- `integration/AvailabilityIntegrationTest` — доступность и работа с часовыми поясами.
- `integration/BookingConcurrencyIntegrationTest` — восемь конкурентных транзакций на настоящей H2.
- `unit/service/BookingServiceTest` и `AvailabilityServiceTest` — сервисы с Mockito-подменами зависимостей, без Spring и БД: успешные сценарии, ошибки и отсутствие записи при отказе.
- `unit/validation/BookingIntervalValidatorTest` — правила интервалов с фиксированными часами, включая наносекундные границы, пустые значения и разные смещения времени.
- `support/` — общая настройка интеграционных тестов, очистка БД, HTTP-помощники и фиксированные часы. Тестовых сценариев здесь нет.

Запуск всех тестов: `./gradlew test`. Для отдельных уровней:

```bash
./gradlew test --tests 'com.example.meetingrooms.unit.*'
./gradlew test --tests 'com.example.meetingrooms.integration.*'
```

Юнит-тесты проверяют решения отдельных классов; транзакции, SQL и HTTP-контракт проверяются интеграционными тестами.

Блокировка комнаты, проверка пересечений и сохранение брони выполняются в одной транзакции `BookingService.create` с уровнем `READ_COMMITTED`.

Ресурсы в `src/main/resources`:

- `schema.sql` / `data.sql` — схема, ограничения, индекс и начальные комнаты.

## Границы решения

H2 хранит данные только в памяти процесса: при перезапуске приложения все брони теряются, комнаты создаются заново. Несколько контейнеров имеют независимые базы, поэтому этот вариант запуска рассчитан на один экземпляр сервиса. Для общей базы и нескольких экземпляров потребуется внешняя СУБД и повторная проверка блокировок на ней.

Аутентификации и проверки владельца брони нет: email является переданным клиентом атрибутом, любой клиент API может отменить любую бронь. Это демонстрационный сервис без интеграции с учетными записями сотрудников. H2 Console не включена.

# Система бронирования переговорных комнат

REST-сервис на Java 21 и Spring Boot 3.5.0. Доступ к данным реализован через Spring Data JPA, данные хранятся в H2 in-memory, схема управляется Flyway. HTTP-контракт описан в OpenAPI и используется для генерации интерфейсов и DTO.

## Быстрый запуск

Через Docker Compose:

```sh
docker compose up --build -d
```

API будет доступно по адресу `http://localhost:8080`. Проверка:

```sh
curl -i http://localhost:8080/api/bookings
```

Остановка: `docker compose down`.

Локальный запуск требует JDK 21. Gradle отдельно устанавливать не нужно:

```sh
./gradlew clean build
java -jar build/libs/meeting-rooms.jar
```

Запуск тестов: `./gradlew test`. OpenAPI-схема работающего сервиса доступна по адресу `http://localhost:8080/openapi.yaml`.

## REST API

| Метод | Путь | Результат |
|---|---|---|
| POST | `/api/bookings` | `201 Created`, созданная бронь и `Location` |
| GET | `/api/bookings?cursor=...&size=20` | `200 OK`, страница бронирований |
| DELETE | `/api/bookings/{id}` | `204 No Content` |
| GET | `/api/rooms/{room}/availability?startsAt=...&endsAt=...` | `200 OK`, доступность комнаты |

`id` — UUID бронирования. Доступные комнаты: `room-1`, `room-2`, `room-3`.

### Создание бронирования

```sh
curl -i -X POST http://localhost:8080/api/bookings \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: booking-20300115-001' \
  -d '{
    "roomId": "room-1",
    "employeeEmail": "ivan@example.com",
    "startsAt": "2030-01-15T10:00:00Z",
    "endsAt": "2030-01-15T11:00:00Z"
  }'
```

Пример ответа:

```json
{
  "id": "b48d70d5-fc2f-4371-96fc-ec0d1426ccfb",
  "roomId": "room-1",
  "employeeEmail": "ivan@example.com",
  "startsAt": "2030-01-15T10:00:00Z",
  "endsAt": "2030-01-15T11:00:00Z",
  "createdAt": "2026-09-09T12:00:00Z"
}
```

Даты в примере должны оставаться будущими относительно часов сервера.

### Получение списка

```sh
curl 'http://localhost:8080/api/bookings?size=20'
```

Первый запрос выполняется без `cursor`. Ответ содержит `content`, `size`, `nextCursor` и `hasMore`. Если `hasMore` равен `true`, передайте полученный `nextCursor` в следующий запрос:

```sh
curl -G http://localhost:8080/api/bookings \
  --data-urlencode 'cursor=<nextCursor из предыдущего ответа>' \
  --data-urlencode 'size=20'
```

Cursor непрозрачен для клиента и основан на стабильной сортировке `(startsAt, id)`. Такая пагинация не использует `OFFSET` и не требует `COUNT(*)`, поэтому её стоимость не растёт с номером страницы. Размер страницы — от 1 до 100, значение по умолчанию — 20.

### Проверка доступности

```sh
curl -G http://localhost:8080/api/rooms/room-1/availability \
  --data-urlencode 'startsAt=2030-01-15T13:00:00+03:00' \
  --data-urlencode 'endsAt=2030-01-15T14:00:00+03:00'
```

Пример ответа:

```json
{
  "roomId": "room-1",
  "startsAt": "2030-01-15T10:00:00Z",
  "endsAt": "2030-01-15T11:00:00Z",
  "available": false
}
```

Проверка доступности не резервирует комнату. После ответа `available: true` конкурентное создание всё ещё может вернуть `409 Conflict`.

### Отмена бронирования

```sh
curl -i -X DELETE \
  http://localhost:8080/api/bookings/b48d70d5-fc2f-4371-96fc-ec0d1426ccfb
```

## Бизнес-правила

1. Комнаты создаются заранее миграцией: `room-1` — «Альфа», `room-2` — «Бета», `room-3` — «Гамма». Неизвестная комната возвращает `404`, чтобы опечатка не создавала новую переговорную.
2. Длительность бронирования — от 15 минут до 4 часов включительно. Минимум отсеивает случайные короткие интервалы, максимум не позволяет занять комнату на весь день.
3. Начало не может находиться в прошлом. Сравниваются точные моменты времени без округления.
4. Время передаётся в ISO 8601 с обязательным смещением, например `2030-01-15T10:00:00Z` или `2030-01-15T13:00:00+03:00`. Ответы нормализуются в UTC.
5. Интервалы полуоткрытые: `[startsAt, endsAt)`. Поэтому брони 10:00–11:00 и 11:00–12:00 совместимы, а любое фактическое пересечение запрещено.
6. Один сотрудник может одновременно организовывать встречи в разных комнатах. Email обязателен, проверяется и приводится к нижнему регистру.
7. Отмена физически удаляет бронь и сразу освобождает интервал. Повторная отмена возвращает `404`.
8. Список содержит все неудалённые брони, включая прошедшие, сортируется по времени начала и UUID и выдаётся страницами через cursor.
9. Ограничения по рабочим часам, выходным и горизонту планирования не вводятся, поскольку их нет в задании.

## Конкурентность и идемпотентность

Создание выполняется в одной транзакции. Сначала сервис отклоняет некорректный интервал, затем блокирует строку комнаты через `SELECT ... FOR UPDATE`, повторно проверяет, что начало не успело оказаться в прошлом, проверяет пересечения и сохраняет бронь. Поэтому некорректные запросы не занимают блокировку, а из нескольких конкурентных запросов на одну комнату и один интервал успешным будет только один.

Необязательный заголовок `Idempotency-Key` защищает от повторной отправки POST:

- одинаковый ключ и одинаковый нормализованный запрос возвращают исходный ответ;
- одинаковый ключ с другим запросом возвращает `409 Conflict`;
- история ключа хранится 24 часа, в том числе после отмены брони;
- повтор запроса для уже отменённой брони возвращает `409 Conflict` и не создаёт встречу заново.

Снимок исходного ответа хранится отдельно от таблицы активных бронирований. Пока бронь активна, повтор возвращает исходный ответ с тем же UUID. После отмены сервер больше не возвращает `201 Created` и `Location` для несуществующей брони. Просроченные ключи удаляет отдельная фоновая задача раз в час; расписание настраивается свойством `app.idempotency.cleanup-cron`. После очистки ключ можно использовать как новый.

Таймаут ожидания блокировки составляет 10 секунд. При его превышении сервис возвращает `503 Service Unavailable` и `Retry-After: 1`.

## Ошибки

Ошибки возвращаются как `application/problem+json`:

| Код | Причина |
|---|---|
| 400 | Некорректный JSON, параметры, UUID, email или интервал |
| 404 | Комната или удаляемая бронь не найдена |
| 409 | Пересечение броней, повтор отменённой операции или конфликт ключа идемпотентности |
| 503 | Истёк таймаут ожидания блокировки |

Для ошибок валидации полей ответ дополнительно содержит массив `errors` с полями `field` и `message`.

## Архитектура и проверка

- `src/main/openapi` — исходный OpenAPI-контракт;
- `controller` — HTTP-контроллеры и преобразование моделей;
- `service` — не зависящие от HTTP бизнес-сценарии, команды и транзакции;
- `repository` — Spring Data JPA-репозитории;
- `validation` — правила допустимого интервала;
- `db/migration` — миграции Flyway.

Интеграционные тесты используют настоящую H2 и фиксированные часы. Они проверяют жизненный цикл брони, пересечения, валидацию, пагинацию, миграции, часовые пояса, конкурентные запросы и идемпотентность. GitHub Actions при push и pull request выполняет полную сборку и отдельно проверяет сборку Docker-образа.

## Границы решения

H2 хранит данные только в памяти процесса, поэтому после перезапуска брони и история идемпотентности теряются. Решение рассчитано на один экземпляр сервиса. Аутентификации нет: email передаётся клиентом, и любой клиент API может отменить любую бронь.
